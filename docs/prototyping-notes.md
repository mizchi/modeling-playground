# ゲーム制作環境の試作記録

記録日: 2026-09-09

対象: media-studio のBGM・効果音、modeling-playground のモデル・Viewer・IRON YARD・Scene Studio。
参照点: media-studio `035fe2c`、modeling-playground `c4a199b`。
現在の操作・実装の詳細は [Scene Studio](scene-studio.md) を参照する。

## 現在の方針

今はプロトタイピングと割り切り、ゲームを作る過程で必要になった画面や操作を試す。
本格的な設計・実装は、リファクタリング中のkaguraへ接続するときに行う。
この記録はその際の判断材料であり、確定した仕様や実装予定表ではない。

優先して残すのは、役立った確認方法、データの意味、再現手順、利用者の評価。
現在のReactコンポーネント、API、JSON形式をそのまま本番に持ち込むことは前提にしない。
試作内で入力・状態の整合性を保つことと、長期互換性を保証することは分けて扱う。

## 今回よかったことと、その根拠

### 1. 素材からゲーム内での確認までつながった

**実装で確認:** 既存のSTRIX・BASTIONモデルに、media-studioの戦闘BGMと5種のSEを接続した。
配置・攻撃設定を変更して同じシーンを試遊し、3ウェーブの勝利、時間切れ、再出撃まで確認できた。

**残したいこと:** 素材単体のViewerや試聴に加え、実際に使う場面で確認できる経路を用意する。
SEは単体の音質だけでなく、連射時の重なり、BGMとの音量関係、命中時のタイミングを確認する必要がある。
E2Eの成功は操作経路が成立する根拠であり、ゲームの面白さや演出の気持ちよさの保証ではない。

### 2. 設定・状態遷移・表示を分けると、違う確認画面に使えた

**実装・テストで確認:** Scene / Actionをデータとして持ち、戦闘処理はDOMや音声に依存しない関数にした。
攻撃プレビューと試遊で同じ `advanceCombat` を使い、弾が実際に当たることを確認した。
シーンの編集履歴はスナップショットで持ち、試遊から戻っても編集内容を保持できた。

**残したいこと:** ドメインの意味を持つ処理はビューから切り離す。
複数のビューを作るときも、それぞれが別の命中判定や保存処理を持たないようにする。
今回のスナップショット方式が大規模なデータにも適するかは未検証。

### 3. 演出は描画結果から推測せず、実際のイベントに接続できた

**実装・テストで確認:** 発射・命中・撃破などをイベントにしたことで、1フレーム内に発生して消える弾も検出できた。
音声側ではイベントIDによる重複防止と同時発音数の制限を実装した。

**残したいこと:** 「何が起きたか」と「それをどう見せる・鳴らすか」を分離する。
同じイベントを音声、エフェクト、診断表示などへ渡せる形は、カスタムビューにも使える候補。
現在は同一JSプロセス内の呼び出しであり、プロセス間転送や同期は検証していない。

### 4. 再生とシークを分けると、途中の状態を安全に確認できた

**実装・テストで確認:** 攻撃プレビューは時刻から状態を再計算し、逆方向のシークにも対応した。
手でタイムラインを動かす操作では音を鳴らさず、再生操作で音声イベントを消費する。
一時停止中の進行停止や、再出撃時の状態リセットも確認した。

**残したいこと:** 作業用の時刻操作と、ライブなゲーム実行を別の操作として定義する。
短い攻撃の再計算は成立したが、長い戦闘全体のリプレイ性能や完全な再現性までは確認していない。

### 5. エンジン内部型を含めない配置データは、MoonBitからも読めた

**実装・テストで確認:** バージョン、アセットID、単位、座標系を明示した同じJSONから、独立したMoonBitパッケージで `mizchi/three` の23ノードを生成できた。
座標・建物サイズ・未知バージョンの拒否を検証した。音源の出典とSHA-256も記録した。

**残したいこと:** リソースの識別、座標・時間の意味、元データへの追跡可能性。
確認できたのは配置の互換性であり、kagura統合、GLB・アニメーション・戦闘・音声のMoonBit移植ではない。

## 利用者の評価から残すこと

- **BGM:** 最初の3曲を残した。戦闘曲ではリズムの単調さが指摘され、裏拍・シンコペーション・和声の変化を求められた。後の2案は採用されなかった。
- **修正の進め方:** この試行では、逐次修正より一度作り直したほうがよさそう、という評価があった。AI一般の能力の結論にはせず、採用済みの版を維持して候補を比較できることを次の試作へ持ち越す。
- **SE:** 爆発・決定・キャンセル・剣ヒット・打撲の5種は「いい感じ」と評価された。短い一括試聴と、個別のゲーム用素材を用意した。
- **制作画面:** 汎用エディタに機能を積むより、分割ペーン、共通Viewer、ゲームのドメインに応じたカスタムビュー、その組み合わせとして一般化したい、という方向が出た。

音声形式・ループ長・衝突判定などの自動検証と、聴感・操作感・制作体験の評価は別に記録する。

## 次に試したい仮説: リソースAPI + カスタムビュー + レイアウト

以下は議論から得た仮説。分割ペーン基盤、汎用リソースAPI、ビュー生成基盤はまだ実装・検証していない。
現在のScene Studioは固定の画面構成であり、この一般化の有効性を証明したものではない。

AIへ指示しながら制作すると、作業ごとに確認したい対象と角度が変わる。
共通のモデルViewerや音声プレイヤーを残しつつ、必要なドメイン別ビューを小さく作り、配置を組み替えられる環境を試す。

| 候補となる共通部分 | 試したい役割 |
| --- | --- |
| ワークスペース | ペーン分割、タブ、ビューの配置、レイアウト保存 |
| リソースへのアクセス | IDでの参照、検索、変更の購読、版と依存関係の確認 |
| 編集の入口 | ドメイン別の型付きコマンド、検証、Undo、変更通知 |
| 作業コンテキスト | 選択対象、再生時刻、比較する版、プレビューセッション |
| 共通ビュー | モデル・音声・ツリー・基本Inspector |
| カスタムビュー | 攻撃判定、敵AIの行動、ウェーブ進行など、そのゲームに必要な確認 |

読み取りを共通化しても、編集を何でも書き換えられるCRUDに寄せる必要はない。
「敵を別の波へ移す」などの意味と制約はドメイン側で持ち、人間とAIが同じ編集経路を使う形を候補とする。
ビューが一時的・再生成可能でも、編集したデータや履歴までビューの寿命に巻き込まれないことを確かめたい。

ビュー同士は直接結合せず、共通のリソースと作業コンテキストを参照する案を試す。
レイアウトには配置に加え、何を同期するかも必要になりそう。
たとえば攻撃検証では3D・判定・音声の時刻を共有し、改訂前後の比較では時刻だけ共有して版は分ける。
同期させたくないビューもあるため、全画面で単一の選択や時計を強制するかは未決定。

## 当面の試行と、観察すること

試行順や採用は固定しない。必要が生じたものから小さく作る。

| 試行例 | 観察すること |
| --- | --- |
| 同じ攻撃を3D・判定・音声で見る | 原因の特定に役立つか。選択と時刻がずれないか |
| 配置用と攻撃検証用のレイアウトを切り替える | 編集途中の状態を保てるか。作業の切り替えが分かりやすいか |
| 採用済みと修正候補を並べる | 元の版を失わず、違いを評価して採否を決められるか |
| AIにその場限りの診断ビューを作らせる | 欲しい情報が得られるか。作る手間が確認の価値に見合うか |
| 別ドメインのビューを追加する | 共通部分をほぼそのまま使えるか。無理な抽象化を要求しないか |

今は完全なプラグインSDK、全リソースの統一スキーマ、永続形式の長期互換性、共同編集などを先回りして作らない。
必要な変更と検証は行いながら、試作コードの置き換えや、うまくいかなかった案の破棄を許容する。

## kagura接続時に再評価すること

1. 複数の実験で繰り返し役立った操作とデータだけを共通基盤の候補にする。
2. kaguraのその時点の設計に合わせ、リソースの所有者、編集コマンド、実行状態との境界を決める。
3. ビューの寿命、購読解除、非同期ロード、エラー、版の競合、Undoの範囲を本番向けに設計する。
4. 長時間の実行・大量データ・レイアウト復元について、試作で未確認だった性能と整合性を検証する。
5. 現在の実装を再利用するか書き直すかは、その評価で決める。まずデータと利用シナリオを移植の検証材料にする。

## 追記: 音声機能を同じリポジトリへ集約（2026-09-09）

**判断:** media-studioの機能も modeling-playground に移す、という利用者の提案を受け、`audio/` に作曲・合成・検証コード、テスト、採用済み素材とライセンスをまとめた。
元のmedia-studio `035fe2c` は出典として残し、以前の観察記録のリポジトリ名も当時の名称を維持する。

**変更:** ルートの `just audio-*` から生成・検証でき、ゲームは同じ `audio/output/` のWAVを直接読む。
試作で使っていたゲーム専用コピーをなくし、生成と組み込みの間に素材の同期作業を挟まない構成にした。

**検証したこと:** 移行先で全曲・SEを再生成し、音声関連14テストを通した。元リポジトリのコード・テスト・ライセンス・素材の51ファイルを照合して保持した。
再生成した戦闘MP3のタイトルタグには違いがあったが、デコード後の音声は一致した。採用済みファイルのタグも保存するため、移行には元MP3を使用した。
配布用ビルドも `tests/pages/studio.spec.ts` で、サブディレクトリからの全6音源の読込とBGM再生を確認した。
その後、リポジトリの肥大化を避けるため、WAV・MP3はコミットせずローカルとCIで再生成する方針にした。コード・譜面・プリセット・出典をGit管理し、過去の音源を含むGit履歴は書き換えない。
リポジトリを集約したこと自体で、前述の汎用リソースAPIや分割ペーン基盤が実装されたわけではない。
