# Pixel Motion Lab: 素体から歩行スプライトを作る

## 今回の到達点

### 追加調査: 別の頭身のフレームが混ざって見える

頭部の1px程度の変動と、「8頭身の再生中に2・3頭身のような別サイズのコマが混ざる」という報告は別問題。下記の頭部固定だけで後者を解決したとは扱わない。

`tests/e2e/sprite-playback-isolation.spec.mjs` では、ローカルChromiumで自動再生しながら、メイン表示・8コマ一覧・4種類の比較欄の実画素を、頭身・方向・色分け・位相を明示して生成した期待値と照合する。8→2→3→8→4→旧素体→8の切替、全8方向、色分けON/OFF、各条件の全8コマを確認する。メインの接地マーカー領域とコマ一覧の選択線は比較対象外。ラベルや画像が単に異なることだけでは混入防止の検証にならないため、意図的に8頭身の表示へ2頭身の画素を入れる負例も検出する。

この条件では混入を再現していない。その後、ユーザーから「WebKitのプレビューだけで発生し、Chromeでは再現しない」と確認された。ユーザーの判断でここで調査を止める。WebKit側の根本原因は未特定・未修正であり、データ混入が原因だと確定したわけではない。この調査では生成形状・フレームデータを変更していない。再調査時はまずWebKitのプレビュー環境で再現する。

### 追加リテイク: 8頭身の頭部固定と2頭身

8頭身の頭が不揃いという指摘を受けて、生成済みフレームの頭部色を測定した。3D寸法は一定でも、サブピクセルの位置・正投影・鼻の突き出しにより、頭部の占有範囲は幅3〜4px、高さ4〜5pxへ変化していた。約5pxの頭では1pxの差が大きいため、骨格の寸法だけを検証しても防げなかった。

対策として8頭身のみ `sprites/pixel-head.mjs` の方向別パーツを使用する。共通の4×5pxマスク（16画素）に収まる陰影・目を持ち、位置だけを3D素体の頭中心から整数ピクセルへ丸めて受け取る。鼻や目でマスクを広げず、コマごとに再ラスタライズしない。首は胴体側の色に分離し、頭と首の色の連結で大きさが変わって見えることも避ける。全体共通の1px外輪郭はこの4×5pxとは別。

- 修正後の実フレームを全8方向×32位相で測定し、頭部は常に幅4px・高さ5px・16画素。位置合わせ後の頭部ピクセル列も同一方向では完全一致。
- 8頭身以外の頭部は従来の3D投影のまま。すべての体型でピクセル揺れを解決したという意味ではない。
- 小さな頭部は最終段階で胴体へ合成する。この歩行では腕が頭を横切らないため成立するが、頭を手で隠すなどの動作には部位の前後関係を扱うマスクが必要。
- [8頭身の歩行コマ](../output/sprite-8head-stable-walk.png)を追加。PNG書き出しとプレビューは同じ補正を使用する。

2頭身 (`2head`) も追加した。身長1.76・頭高0.88、頭高は投影前換算で19.36px。胴体以下を短くし、骨盤幅と四肢の太さも調整。上下腿の合計は約0.499、歩幅約0.250、1周期の移動量約0.499。既存の骨長・接地・ループ・全方向のはみ出し検証に含めている。

比較欄は8・4・3・2の4種類。スマートフォンでは2列にし、同じ整数倍率で表示する。出力は `sprite-walk-2head-{debug,neutral}.png` と `sprite-walk-2head.json`。各JSONの `headRendering` に3D投影か固定ピクセルパーツかを明記する。

画像生成で32枚を一括作画する方法から、同じ3D素体・歩行位相を8方向へ投影する方法に切り替えた。今回は**衣装のない歩行素体の検証**。ロマサガ3風の完成キャラクターや汎用アニメーション生成器ではない。

- 起動: `just dev` → `http://127.0.0.1:5188/sprite-lab.html`
- 再生成: `just sprite-walk`
- 単体テスト: `node --test tests/sprite-walk.test.mjs`
- UIテスト: `pnpm exec playwright test tests/e2e/sprite-lab.spec.mjs`
- 本番パス: `just test-pages`

## 正本と出力

### 頭身プリセットの追加検証

8頭身・4頭身・3頭身を追加。元の約5頭身も `legacy` として保持した。初期表示は4頭身。3種類の比較欄は同じ方向・位相・整数倍率で同期し、選択中の体型に対応したPNG・JSONへダウンロード先も切り替わる。

直立時の身長は全種類1.76で固定。頭身は「身長÷頭頂から顎までの高さ」と定義し、頭の高さを決めて残りの胴体・四肢の長さを再計算する。肩幅・骨盤幅・手足の太さもプリセットで調整する。頭だけを差し替える方式ではない。

| プリセット | 頭の高さ（投影前の論理px換算） | 上下腿の合計長 | 歩幅 | 1周期の移動量 |
| --- | --- | --- | --- | --- |
| 8頭身 | 4.84px | 0.874 | 0.437 | 0.874 |
| 4頭身 | 9.68px | 0.749 | 0.374 | 0.749 |
| 3頭身 | 12.91px | 0.666 | 0.333 | 0.666 |

周期は共通0.8秒。脚が短いほど歩幅・持ち上げ・上下動も小さくするため、速度は同じではない。歩行位相は同じで、接地側と腕振りの対応も変えない。歩幅の定義は一方の足の接地期間中の相対移動距離で、1周期のルート移動量はその2倍。

検証結果:

- 各プリセットを200位相でサンプリングし、上下腕・上下腿の長さ、交互の接地、足の高さを確認。ワールド空間の接地足の移動誤差はテスト許容値1e-8以内。
- 3種類＋旧素体それぞれ全8方向×8コマで、画像のはみ出し、パレット範囲、生成の決定性を確認。PNGと生成コードの完全一致、JSONの関節座標も検証。
- 8・4・3頭身の色分け版は全方向で8コマすべて異なるピクセル列。ただし「コマが異なる」ことは自然な歩行の証明ではない。
- 比較UIの位相同期、体型の変更前後で位相を維持すること、PNG/JSONの切替、モバイルの共通整数倍率をE2Eで確認。
- [側面比較](../output/sprite-proportions-side.png)、[正面比較](../output/sprite-proportions-front.png)、[斜め背面比較](../output/sprite-proportions-rear-quarter.png)を出力。

所見: 骨格・接地・出力の経路は体型間で共有できる。32×48pxの8頭身は頭が約5pxと小さく、目鼻が潰れやすい。4・3頭身は顔の情報を載せる余地が増える。これは素体画像の比較結果であり、髪・衣装を含む完成キャラクターの品質を保証しない。頭身別の輪郭・顔・コマの補正が次の課題。

出力は `sprite-walk-{8head,4head,3head}-{debug,neutral}.png` と `sprite-walk-{8head,4head,3head}.json`。旧ファイル名は旧素体のまま残す。JSON version 2には頭身情報・体型別の骨長/歩幅・各コマの関節位置を含む。再生成: `just sprite-walk`。

| 層 | ファイル | 責務 |
| --- | --- | --- |
| 仕様 | `sprites/definition.mjs` | サイズ、パレット、方向、骨の長さ、歩幅 |
| 動作 | `sprites/motion.mjs` | 位相から関節座標・接地状態を算出。DOM・時刻・描画に依存しない |
| 描画 | `sprites/raster.mjs` | 立体の部位、正投影、Zバッファ、離散陰影、輪郭 |
| 操作 | `sprites/lab.mjs` | 再生時刻、コマ送り、方向、表示設定 |
| 出力 | `scripts/build_sprite_walk.mjs` | 同じ描画コードからPNG・JSONを出力 |

最終フレームの正本は32×48要素の `Uint8Array`（パレット番号）。フルカラーの高解像度画像を縮小したものではない。PNG境界でRGBAへ変換する。パレット0は透明、他は完全不透明。輪郭も1論理ピクセル単位。プレビューは整数倍率で表示し、画像補間はしない。

`output/sprite-walk-debug.png` と `output/sprite-walk-neutral.png` は256×384px。横8コマ、縦8方向。JSONにはフレーム寸法、原点、パレット、周期、接地状態、各位相の3D関節位置を含む。JSONとPNGは再生成可能な出力物であり、直接手修正しない。

## 歩行の契約

- 座標系: Yが上、Zが進行方向。左肢はX負、右肢はX正として命名。
- 周期0.8秒、8コマ。1コマ100ms。位相0〜1を循環し、左右を半周期ずらす。
- 片足が前半周期で接地、後半で遊脚。これは単純化したモデルで、両足接地期間は未実装。
- 接地中の足は素体に対して一定速度で後退する。ルートを周期あたり+Zへ `getRig(id).travelPerCycle` 移動すると、その足のワールド座標は一定になる。旧素体では0.8。
- 遊脚の前後移動はHermite曲線、持ち上げはsin²。接地との境界で前後速度を合わせ、上下速度は0へ戻す。
- 腰の小さな上下動と左右動を入れ、膝・肘を2ボーンIKで求める。届かない目標を骨の伸縮でごまかさない。
- 腕は同じ側の脚と逆向きに振る。胸・腹・骨盤を重ねて、素体が腰で途切れないようにする。

地面表示はルート追従カメラ相当。キャラクターを画面中央に置き、地面の目印を逆向きに移動させる。PNGはその場歩きで、地面・骨格線・接地マーカーを含まない。

原点 `[16,44]` はルート直下の地面の投影位置であり、左右の足先位置ではない。コマごとの自動トリミングや足先への位置合わせをすると、歩行の意味が変わるため行わない。

## 8方向とフレーム

行順は下（正面）、左下、左（側面）、左上、上（背面）、右上、右（側面）、右下。
方向を変えても、キャラクターの左右、骨格、位相は同一。画像の反転で左右の部位を入れ替えない。

最初は左側面で、色分けした足を追う。コマ0〜3で左接地、4〜7で右接地。地面に対する滑りを確認した後、正面・背面・斜めで重なりを見る。接地マーカーは足の下へ描く検証用の印。

## 検証と限界

自動テストは骨長、左右交互の接地、地面より下へ足が落ちないこと、ワールド空間の足滑り、ループ境界、描画の決定性、パレット範囲、透明度、フレーム外へのはみ出し、シートと個別フレームの一致を確認する。UIでは再生・停止・コマ送り・方向切替・モバイルの整数倍表示、本番ビルドではPNGとJSONの取得を確認する。

これらは「自然で魅力的な動き」の保証ではない。連続座標が正しくても、ピクセルへの量子化で輪郭が1px変わることはある。8・4・3頭身を比較できるが、ロマサガ3風の顔・服装はまだ実装していない。現在は踵からつま先への足の回転、両脚支持、胴体の本格的な捻り、髪・布の遅れも省略している。

## 次の工程

1. 横向きの歩行をユーザーが再生して評価し、歩幅・持ち上げ・テンポ・頭身を固定する。
2. 素体の部位に紐づく髪・服・配色を別レイヤーとして追加する。
3. 特定方向での顔の読みやすさ、輪郭、手足の太さを低解像度専用の補正として管理する。
4. 4コマ化は8コマ版を確認してから。単純な間引きで接地や左右の差が消えないか再生確認する。
5. ニッチな動きには道具・接触点・軌道の契約を追加する。今回の歩行モデルだけで傘やハンドルなどを扱えるとはしない。

既存の生成画像 `romasaga3-traveler-draft.png` はデザイン参考として残す。背景除去・格子推定は今回の経路では使っていない。[Pixel Makerの記事](https://zenn.dev/holometer/articles/pixel-maker-ai-correction)が扱う既存画像の格子補正とは異なり、初めから固定の論理ピクセルへ描画する方式を試している。
